# База метрик до этапа Э9

Версия 1.0 от 06.10.2026. Основание — решение допроса Э9-12 (`10_QUIZ.md`): база снимается воспроизводимым замером по данным продукта и числами заказчика для того, чего в продукте нет. Фиксация базы — одно из трёх условий начала кода этапа Э9 (`06_PLAN.md`, пункт 6.5 и раздел Э9).

## 1. Зачем

Этап Э9 переносит в продукт согласование возмещаемых чеков и приёмку актов заказчиком, показывает ему расчёты с графиком и напоминает письмом. Через месяц после запуска на вопрос «стало ли быстрее» можно ответить только против величин «до», снятых тем же правилом, каким будут сниматься величины «после». Порог, подогнанный под факт задним числом, мерилом не является.

База состоит из двух частей:

- **замер скриптом** — четыре метрики по данным продукта, воспроизводимо, тем же правилом до и после;
- **форма заказчика** — метрики вне системы: переписка в мессенджере, выезды, сверка с прорабом, — по трём последним объектам.

## 2. Замер скриптом

Правило — `packages/domain/src/baseline.ts` (проверено тестами `baseline.test.ts`); чтение базы — `scripts/measure-baseline.mjs`. Окно по умолчанию — 90 дней по сегодняшний день организации включительно; дни считаются по часовому поясу организации, как во всём продукте с этапа Э8. Транши отбираются по дню закрытия, чеки — по дню записи: замеряется то, что началось в окне, а исход — к его концу.

| № | Метрика | Что считается | Откуда | Ожидаемое после Э9 |
|---|---|---|---|---|
| М-1 | Дни от закрытия транша до оплаты | медиана и наибольшее по оплаченным; доля оплаченных в срок по договору среди траншей с известным исходом; перечень просроченных без оплаты | день закрытия транша, дни платежей со сторно, отметка «оплачен» | медиана ниже, доля в срок выше: заказчик видит «оплатить до» (ДР-6) |
| М-2 | Дни от закрытия транша до подписи акта | медиана и наибольшее по подписанным; дольше всех неподписанный | отметка подписи акта руководителем | ниже: акт ждёт заказчика в очереди и письме (ДР-2б, ДР-10) |
| М-3 | Входы заказчика | доля заходивших среди действовавших входов; дней с заходом в неделю, медиана по входам не короче недели | сохранившиеся сессии и отметка захода | выше: колокол и письмо «ждёт вас» (ДР-10) |
| М-4 | Разбор чеков | доля разобранных среди ждавших разбора; дни от записи до решения; дольше всех без решения | чеки, состояние и день решения | не хуже: подтверждение заказчиком не должно задерживать решение руководителя (ДР-2а) |

**Правила, которые читатель числа должен знать.**

- Оплаченным транш становится в день, с которого платежи покрывают его сумму и уже не перестают покрывать: сторно отменяет и день оплаты. Отметка «оплачен» без покрывающих платежей даёт день отметки — верхнюю оценку: деньги приходят раньше, чем их отмечают. Оплата раньше закрытия считается нулём дней.
- Просрочка — тем же правилом, что на экране денег: порог по договору заказчика, при пустом поле — семь дней; ровно порог — ещё в срок.
- Чек руководителя, подтверждённый им же при записи, разбора не ждал и в сроки разбора не входит: иначе ноль дней руководителя разбавил бы ожидание прораба.
- Считаются дни с заходом, а не сессии: два входа за вечер — один интерес к объекту.

**Ограничения.**

- Истории заходов продукт не хранит: сессия удаляется при выходе и при снятии входа, отметка захода держит только последний. М-3 — нижняя граница; после Э9 её точнее заменит счётчик колокола.
- Замер видит данные на момент запуска. Запись, поправленная задним числом, меняет и повторный замер того же окна; поэтому вместе с отчётом сохраняются числа `--json`.
- Согласование чеков заказчиком до Э9 идёт вне продукта, и М-4 его не видит: эта часть базы — в форме (Ф-3).

**Запуск** — на рабочей базе, только чтение, без обращения в сеть:

```
DATABASE_URL=… node scripts/measure-baseline.mjs [--from ГГГГ-ММ-ДД] [--to ГГГГ-ММ-ДД] [--json путь]
```

Отчёт печатается по каждой организации; в нём нет персональных данных — только числа и коды объектов. Замер «после» берётся окном той же длины.

**Стенд замер проверяет, но базу не снимает**: данные стенда придуманы. `scripts/verify-baseline.mjs` в задании «Стенд» сверяет замер с продуктом — просрочку и оплаченность с экраном денег, чеки без решения с вкладками «Чеки», — требует непустого случая у каждой метрики и проверяет, что скрипт замера не пишет в базу.

## 3. Форма заказчика

Заполняется по трём последним объектам с закрытым траншем. Источник — переписка в мессенджере, календарь руководителя и сверка с прорабом за последние четыре недели работ на объекте. Число, которого нет, пишется словом «неизвестно», а не оценкой: оценка, записанная как число, становится базой, которой не было.

| № | Метрика | Как считать | Объект 1 | Объект 2 | Объект 3 |
|---|---|---|---|---|---|
| Ф-1 | Обращений заказчика в мессенджере за неделю | все вопросы заказчика к студии, среднее за четыре недели | | | |
| Ф-2 | Из них — о деньгах | «сколько и когда платить», «за что этот платёж», «что за чек» | | | |
| Ф-3 | Согласование чеков заказчиком | чеков, отправленных на согласование за месяц; дней от отправки до ответа, обычно и дольше всех | | | |
| Ф-4 | Дней от передачи акта до подписанного экземпляра | по последнему акту; если в продукте отметка подписи ставилась в день получения — сверить с М-2 | | | |
| Ф-5 | Выездов руководителя на объект в неделю | по календарю, среднее за четыре недели | | | |
| Ф-6 | Доля чеков, дошедших до продукта | чеков в продукте к фактическим закупкам по объекту; цель раздела 9 `01_PROJECT.md` — не ниже 90 % | | | |
| Ф-7 | Доля принятых в продукте позиций | принятых позиций к фактически выполненным по сверке с прорабом; цель — не ниже 80 % | | | |

## 4. Состояние базы

| Часть | Состояние |
|---|---|
| Правило замера и тесты | готово |
| Скрипт замера и проверка на стенде | готово |
| Замер скриптом на рабочей базе | не выполнен — запускает заказчик или исполнитель с доступом к рабочей базе |
| Форма по трём объектам | не заполнена — заполняет заказчик |

База считается зафиксированной, когда обе последние строки заполнены и отчёт замера с числами `--json` приложен к этому документу датированной записью.
