## Статус

**Принято 06.11.2026** ответами 3 «б» и 8 «а» раунда 1 (`docs/discovery/QUESTIONS.md`; запись —
`docs/10_QUIZ.md`, раздел «Раунд 1 допроса фазы 0 переработки, 06.11.2026»). Роль бригадира в вебе со
сдачей раздела на приёмку — без права приёмки, без цен, ставок и сумм, без работы без сети; иных новых
ролей нет. Условие предлагаемого решения — у бригад заказчика есть бригадиры, способные сдавать раздел
с телефона, — записано утвердительным по ответу «б», данному с возражением 1 на виду; подтверждение
спрашивается перед этапом вместе с Д7. Отмена `docs/01_PROJECT.md:63` редакции 1.19 в части бригадира записана прямо
редакцией 1.20 (разделы 3 и 6.4). Работа — этап Э13 `docs/06_PLAN.md`, после исправлений входа ADR-0008;
начинается после ответов второго раунда на Д7, Д8 и Д14.

Прежняя запись: ~~Требует решения заказчика.~~ Отменяет в части записанное решение «рабочие в контур ввода данных не
входят вообще» (`docs/01_PROJECT.md:63`), вводит роль, связь пользователя с бригадой и новую сущность.

## Контекст

**Записанные решения.**

- «Рабочие в контур ввода данных не входят вообще. Прямая цитата: „есть узбеки, которые не могут это
  сделать, поэтому это будет делать прораб“. Любое требование к рабочим обесценивает данные системы»
  (`docs/01_PROJECT.md:63`). Запись не делит рабочих на бригадиров и прочих.
- Приёмка — единственный источник факта выполнения (БП-1, `docs/01_PROJECT.md:199`); ядро — отметка
  прораба (`docs/01_PROJECT.md:26-28`). Риск «прораб перестанет вести приёмку» снижается привязкой к
  расчёту с рабочими и порогом «не более трёх касаний до отметки» (`docs/01_PROJECT.md:230`).
- Заявленное и принятое разведены: заявленная готовность — утверждение, принятое — измерение
  (ред. 1.10, `docs/01_PROJECT.md:379-388`).
- Нативные приложения и работа без сети не требуются (`docs/01_PROJECT.md:238-239`); ДР-12 — манифест
  веб-приложения без сервис-воркера (05.10.2026, `docs/01_PROJECT.md:148`).
- Мастера у этапа нет: «назначения и чужие задачи в объём не входят» (`apps/api/prisma/schema.prisma:764`).

**Что есть в продукте.**

- Четыре роли: `OWNER`, `FOREMAN`, `ACCOUNTANT`, `CLIENT` (`apps/api/prisma/schema.prisma:36-41`,
  `packages/contracts/src/index.ts:25`).
- Бригада — запись справочника без входа и без связи с пользователем (`apps/api/prisma/schema.prisma:590-606`);
  расчёт ведётся с бригадой через бригадира, состав бригады не хранится, вид `PERSON` — для расчёта с
  конкретным мастером (`apps/api/prisma/schema.prisma:68-70`, `:115-118`). Бригада — получатель начисления
  по этапу раздела (`apps/api/prisma/schema.prisma:764-768`, `:783-785`).
- Маршрут без `@Roles` открыт руководителю, прорабу и бухгалтеру; заказчику объекта — только названное
  прямо: «забытый декоратор оборачивается отказом, а не утечкой» (`apps/api/src/common/roles.guard.ts:26-39`).
- Внутренние поля — ставка, фонд оплаты, прибыль (`packages/domain/src/projection.ts:65`); цену единицы
  прораб видит. Сумму начисления бригаде прораб не видит: при известном количестве она выдала бы ставку
  (`apps/web/src/Acceptance.tsx:27-30`).
- Видимость объекта — условием запроса: прорабу — свои объекты, заказчику объекта — объекты его записи
  справочника (`apps/api/src/common/project-scope.ts:17-23`).
- Снимок пакета приёмки обязателен и подчинён пакету (`docs/01_PROJECT.md:187-191`,
  `apps/api/prisma/schema.prisma:899-917`); метаданные снимка снимаются (П-39, `docs/10_QUIZ.md:338`).

**Что предлагает бриф v2.0.** Бесплатное мобильное приложение исполнителя и членов бригады, работающее
без сети: «Сегодня», доступ на объект, сдача этапа не больше чем за три действия, замечания, выплаты,
профиль; одна учётная запись на несколько организаций (бриф v2.0, §7.8.4, §7.4.4).

## Рассмотренные варианты

| Вариант | Суть | Оценка |
|---|---|---|
| а | Решение сохраняется: ни рабочие, ни бригадиры не входят; данные вводит прораб | Без работ; бриф U3 не исполняется |
| б | Роль бригадира в вебе: сдать раздел на приёмку — снимки и отметки «сделано» по позициям; без права приёмки, без цен, ставок и сумм; рабочие вне ввода; без работы без сети | Факт остаётся за прорабом; отменяет `01_PROJECT.md:63` только для бригадиров; без новых справочников |
| в | По брифу: мобильное приложение без сети для бригадира и членов бригады, выплаты, несколько организаций | Отменяет `РБ-1`, `РБ-2`, `РБ-3` (`docs/discovery/GAP.md`, раздел 3) и требует ADR-0006 в реализации |

## Предлагаемое решение

Вариант «б» — при прямом ответе заказчика, есть ли у его бригад бригадиры, способные сдавать раздел с
телефона (возражение 1 к вопросу о входе бригадира, `docs/discovery/QUESTIONS.md`).

1. **Роль.** Пятое значение перечисления ролей, рабочее имя `MASTER`; слово экрана — «бригадир» или
   «мастер» по ответу заказчика (Д7). Роль не входит в перечень умолчания стража
   (`apps/api/src/common/roles.guard.ts:39`): ей открыто только названное прямо, как заказчику объекта.
2. **Связь с бригадой.** Пользователь роли `MASTER` связан ровно с одной записью `Worker` (необязательное
   поле пользователя, уникальное). Вход один на бригаду; члены бригады учётных записей не получают.
3. **Видимость.** Объекты, где бригада пользователя стоит у этапа графика; внутри объекта — разделы её
   этапов. Правило — новой веткой `projectScope` (`apps/api/src/common/project-scope.ts:17-23`), условием в
   запросе к базе, не отбором после выборки.
4. **Поля.** Наименование, единица, количество по смете, принятое и остаток. Цены, ставки, суммы,
   «выполнено на сумму», транши, акты, чеки и деньги объекта в ответах для роли отсутствуют, а не пусты
   (правило `docs/01_PROJECT.md:142`). Адрес, ключи и контакт заказчика объекта — по ответу Д7.
5. **Сдача раздела** — новая сущность «сдача на приёмку» (рабочее имя `HandoverRequest`): объект, раздел
   верхнего уровня этапа бригады, автор, время, комментарий, строки «позиция — заявленное количество»,
   один или несколько снимков. Сдача — **заявленное**: факта выполнения она не создаёт, начисления не
   трогает, в «принято» не входит (БП-1; ред. 1.10).
6. **Приёмка по сдаче.** В очереди прораба (ДР-1, `packages/domain/src/inbox.ts:25`) — пункт «раздел
   сдан бригадой». Прораб открывает лист приёмки с отмеченными позициями и заявленными количествами и
   принимает обычным пакетом (`apps/api/src/acceptance/acceptance.service.ts:425-562`) — с исправлениями
   ADR-0007. Пакет ссылается на сдачу. Снимок пакета — снимок прораба или снимок сдачи, скопированный
   сервером в новый ключ хранилища; выбор — вопрос второго раунда (Д14). Сдача закрывается приёмкой или
   отклонением с причиной.
7. **Без работы без сети.** Повторная отправка при плохой связи живёт, пока страница открыта; закрытая
   вкладка теряет неотправленные снимки, и экран говорит об этом словами (возражение 2 к вопросу о входе
   бригадира). Сервис-воркер не вводится (ДР-12).
8. **Вход** — персональная ссылка из «Людей» по правилам ADR-0008; самостоятельной регистрации нет
   (`apps/api/src/people/people.service.ts:11-14`).
9. **Экраны.** «Мои разделы» (объекты и разделы бригады с остатком) и «Сдать раздел» (отметки,
   снимок, отправка) — до трёх действий; строка в `07_IA.md`, артборд канвы, памятка бригадиру по
   образцу `design/prorab.html`.
10. **Журнал и лента.** Сдача и её закрытие пишутся в журнал и ленту объекта (ДР-5) в той же транзакции.

## Последствия

- Решение `docs/01_PROJECT.md:63` отменяется для бригадиров и сохраняется для прочих рабочих; отмена
  называется прямо в новой редакции `01_PROJECT.md` (ADR-0001).
- Ядро не меняется: начисление по-прежнему порождает только приёмка прораба со снимком ставки (БП-3).
- Прораб получает предварительно заполненный лист и тратит меньше касаний на пакет; при отказе бригадира
  вести сдачу продукт работает как сегодня.
- Новая роль требует проверки на каждом маршруте: сплошная проверка поверх HTTP расширяется на пятую
  роль (`scripts/verify-api.mjs:15-29`, `:282-327` — перечень внутренних полей и обход ответов).
- «Бесплатно» при заказной работе смысла не имеет: платы за пользователя нет (возражение 3).
- Выплаты бригаде, замечания и несколько организаций не вводятся (Д8, вопрос о замечаниях при приёмке,
  Д9 и ADR-0006).
- Оценка: 11,5–15 идеальных дней (`ESTIMATE.md`, раздел 3).

## Зависимости от решений

- Вопрос раунда 1 о входе бригадира в продукт (контур исполнителя, U3): выбор «а», «б», «в».
- Вопрос раунда 1 о ролевой модели за пределами бригадира: пятая роль — только эта.
- Вопрос раунда 1 о персональной ссылке входа и частоте запросов входа: способ входа бригадира (ADR-0008).
- Вопросы второго раунда: Д7 (что видит бригадир и слово роли), Д8 (учётная отметка выплаты), Д9
  (несколько организаций), Д14 (снимки вне приёмки).
