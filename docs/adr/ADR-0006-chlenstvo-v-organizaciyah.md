# ADR-0006. Мультиарендность: членство пользователя в организациях как задел

| Параметр | Значение |
|---|---|
| Дата | 06.11.2026 |
| Фаза | 0 — аудит без изменения кода |
| Состояние продукта | ветка `main`, голова `053cd2c` |
| Блок брифа v2.0 | 80 %, мультиарендность и учётные записи (бриф v2.0, §7.2, §7.3, §7.4.4; чек-лист §8.2, строка 1) |
| Связанные документы | ADR-0001 (порядок решений и обозначения), ADR-0004, `docs/discovery/AS-IS.md` (раздел 3.6), `docs/discovery/ESTIMATE.md` |

## Статус

Предложено. Решение описывает модель и правила, которые сохраняют её дешёвой, и **не вводит кода и
миграций** до решения заказчика о выходе на рынок. Реализация модели — отдельное решение заказчика.

## Контекст

**Записанные решения.**

- Разработка — заказная работа под конкретного плательщика; продуктовый выход на рынок с тиражируемым
  решением на имеющихся данных не обоснован (`docs/01_PROJECT.md:246`).
- Выход за пределы заказчика раньше уровня готовности TRL 7 преждевременен; решать — заказчику
  (`docs/14_MARKET.md:31`, `:100-102`). Гипотеза цены — за организацию, а не за сотрудника
  (`docs/14_MARKET.md:65-69`).
- Регистрация и онбординг компании сняты прежними решениями (`docs/06_PLAN.md:172`); самостоятельной
  регистрации людей нет (решение 13.09.2026, `apps/api/src/people/people.service.ts:11-14`).
- Пилот у самого заказчика не начат: облако РФ, наполнение реальными данными и замер метрик — не
  начаты или заблокированы (`docs/06_PLAN.md:142-146`).

**Что есть в продукте.**

- `Organization` — арендатор по соглашению кода: `orgId` в 11 корневых таблицах, отбор по организации —
  в каждом запросе службы; политик строк в базе нет (`docs/discovery/AS-IS.md`, разделы 1.3, 2.3, 3.6).
- Пользователь состоит ровно в одной организации (`apps/api/prisma/schema.prisma:311-313`); сессия
  разрешается в пользователя с его организацией (`apps/api/src/auth/auth.service.ts:241-261`), и каждый
  обработчик берёт организацию из `RequestUser` (`apps/api/src/common/current-user.ts:4-17`).
- Почта и телефон уникальны по всем организациям только проверкой в коде при выдаче входа
  (`apps/api/src/people/people.service.ts:81-107`); в базе уникальна пара `[orgId, email]`, у телефона
  уникальности нет (`apps/api/prisma/schema.prisma:358`). Вход ищет человека по почте или телефону без
  условия организации (`apps/api/src/auth/auth.service.ts:46`, `:140`, `:177`).
- Видимость объекта — одним правилом в запросе к базе (`apps/api/src/common/project-scope.ts:17-23`).
- Организация заводится только наполнением стенда; вторая организация наполнения — без объектов, с одним
  шаблоном и одним человеком (`apps/api/prisma/seed.mjs:30`, `:909-924`). Проверки «объект, смета и деньги
  организации А не видны пользователю организации Б» поверх HTTP нет (`docs/discovery/AS-IS.md`, раздел 3.6).

**Что предлагает бриф v2.0.** Организация — арендатор с изоляцией данных на уровне хранилища и запросов;
учётная запись исполнителя и заказчика одна на все организации и подключается членством с ролью; тарифы,
регистрация, пилот на 5–10 организациях (бриф v2.0, §7.2, §7.3, §7.4.4, §8.4).

## Рассмотренные варианты

| Вариант | Суть | Оценка |
|---|---|---|
| а | Заказная работа сохраняется; членство описывается заделом без кода; реализация — после TRL 7 и решения о рынке | Совпадает с `docs/01_PROJECT.md:246` и `docs/14_MARKET.md:100`; цена — ноль сейчас |
| б | Заложить фундамент сейчас: членство, общие учётные записи, изоляция в базе — без регистрации и тарифов | Объём без потребителя; меняет вход, сессию и все отборы по организации до первого реального заказчика |
| в | Тиражный сервис по брифу: регистрация организаций, тарифы, пилот на нескольких организациях | Отменяет `docs/01_PROJECT.md:246` и снятую регистрацию (`docs/06_PLAN.md:172`) |

## Предлагаемое решение

Вариант «а». Ниже — модель, которая вводится, когда заказчик решит выход на рынок, и правила, которые
до того держат её дешёвой.

**Модель на будущее (не реализуется).**

1. **Человек** (`Person`): глобальная учётная запись — имя, телефон, почта; телефон и почта уникальны
   в базе, а не только в коде.
2. **Членство** — нынешняя строка `User`: организация, роль, связь с записью заказчика или бригады
   (ADR-0004), дата снятия, последний заход. Таблица `users` не переименовывается; к ней добавляется
   ссылка на человека. Авторство в журнале, приёмке и чеках остаётся за членством — история не
   переписывается (БП-4; П-51).
3. **Сессия** несёт выбранное членство; `RequestUser.orgId` берётся у членства. Человек с несколькими
   членствами после входа выбирает организацию; с одним — входит сразу, как сегодня.
4. **Вход** ищет человека, а не пользователя; коды и ссылки выдаются человеку, обмен открывает сессию
   членства. Пределы частоты ADR-0008 считаются по человеку и по адресу запроса.
5. **Изоляция.** Обязательная проверка поверх HTTP «данные организации А не видны пользователю
   организации Б, в том числе человеку с членством в обеих» — на объектах, сметах, деньгах, снимках и
   файлах. Политики строк PostgreSQL — отдельным решением: требуют передачи организации в соединение на
   каждый запрос и проверки с пулом соединений Prisma; совместимость не проверена.
6. **Перенос данных** (когда решение принято): каждому `User` заводится `Person` один к одному по
   телефону или почте; совпадения по нескольким строкам до переноса выводятся отчётом и решаются
   человеком. План — по образцу `docs/discovery/MIGRATION.md`, раздел 2.

**Правила, действующие уже сейчас, без кода.**

- Новые таблицы получают `orgId` или принадлежат организации через объект или родителя, как сегодня.
- Организация берётся только из `RequestUser`, а не из чтения пользователя в службе.
- Проверка уникальности почты и телефона по всем организациям (`apps/api/src/people/people.service.ts:81-107`) сохраняется.
- Новые маршруты получают проверку чужой организации в `verify-api` по образцу `scripts/verify-api.mjs:473-497`.

## Последствия

- Сейчас — ни схемы, ни кода. Риск — цена переноса растёт с объёмом реальных данных; поэтому модель
  записана до ввода реальных данных, а не после.
- Откладываются части других блоков, завязанные на одну учётную запись в нескольких организациях:
  бригадир нескольких организаций (ADR-0004, Д9), заказчик объекта нескольких организаций, бесплатность
  как довод продаж.
- Проверка изоляции по объектам и деньгам поверх HTTP полезна и без членства; она не меняет схему и
  может войти в работу по вопросу об очереди, если заказчик её выберет (`ESTIMATE.md`, раздел 2.4).
- Оценка реализации модели при решении о рынке — 8,5–14 идеальных дней без политик строк
  (`ESTIMATE.md`, раздел 3).

## Зависимости от решений

- Вопрос раунда 1 о заказной работе или тиражном сервисе для многих организаций: выбор «а», «б», «в».
- Вопрос второго раунда Д10 (модель членства и изоляция данных в базе) — уточняет пункты 1–5 модели.
- Вопрос второго раунда Д9 (работа бригадира и заказчика с несколькими организациями).
