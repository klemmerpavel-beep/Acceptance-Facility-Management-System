## Статус

**Принято 06.11.2026** ответом 15 «б» раунда 1 (`docs/discovery/QUESTIONS.md`; запись — `docs/10_QUIZ.md`,
раздел «Раунд 1 допроса фазы 0 переработки, 06.11.2026»). Пункты 1–7 и 10 исполняются; срок и
многоразовость персональной ссылки сохраняются — решение № 1 полевого испытания (пункт 8, вариант «б»);
пакет `@fastify/rate-limit` не вводится, ограничение пишется своим кодом (пункт 9). Ответом не названы и
спрашиваются при приёмке работы: судьба сессий, уже открытых прежней ссылкой (пункт 4; до ответа они
живут до своего срока, как сегодня), и дата снятия переходного `GET /auth/consume` (пункт 3). Реестр —
П-61, П-62, П-63 `docs/13_FULL_AUDIT.md`; план — раздел «Ф0» `docs/06_PLAN.md`, после ветки дефектов
приёмки.

Прежняя запись: ~~Предложено~~ — в части пунктов 1–7 решения: они не меняют схему, зависимости и записанное решение о
входе по персональной ссылке. Требует решения заказчика — срок и многоразовость персональной ссылки
(пункт 8) и пакет ограничения частоты как новая зависимость (пункт 9). Все пункты вынесены одним
вопросом раунда 1 о персональной ссылке входа и частоте запросов входа; работа начинается после ответа.

## Контекст

**Записанные решения.** Вход прораба по персональной ссылке без регистрации, пароля и кода из SMS —
решение № 1 полевого испытания (`docs/05_MVP_SCOPE.md:28`); ссылка сохранена при добавлении входа по
телефону (`docs/01_PROJECT.md:295`). Предел попыток кода и гашение ссылки условным обновлением (П-24,
`docs/13_FULL_AUDIT.md:68`). Код и токен в ответе — только по флагу стенда; отправщик — к пилоту (П-28,
`docs/10_QUIZ.md:336`). Новая зависимость — решение заказчика (`docs/13_FULL_AUDIT.md:18-20`).

**K5. Токен входа в строке запроса** — подтверждено, тяжесть высокая.

- Адрес персональной ссылки — `${origin}/api/auth/consume?token=…` (`apps/web/src/People.tsx:65-66`); маршрут
  `GET /auth/consume` берёт токен из строки запроса (`apps/api/src/auth/auth.controller.ts:77-89`).
- Персональная ссылка живёт 180 дней и после обмена остаётся действующей (`apps/api/src/auth/auth.service.ts:11-12`,
  `:87-91`); гасится только ссылка из письма (`:105-116`); все выдачи через «Люди» — персональные ссылки
  (`apps/api/src/people/people.service.ts:144`, `:171`, `:202`).
- В `apps/web/nginx.conf:1-18` нет директив `access_log` и `log_format`; `location /api/` проксирует запрос как
  есть (`:8-13`). Встроенный формат журнала nginx включает строку запроса целиком; это свойство nginx, в
  окружении фазы 0 не проверено. API журнала запросов не ведёт (`apps/api/src/main.ts:13`).
- Следствие: кто читает журнал контейнера `web` или балансировщика перед ним, получает вход под чужой
  учётной записью на срок до 180 дней.

**K6. Повторная выдача ссылки не отзывает прежнюю** — подтверждено, тяжесть средняя.

- Комментарий «выдача новой не отзывает старую по отдельности — обмен одноразовый»
  (`apps/api/src/people/people.service.ts:175-182`, описание класса — `:16-17`) противоречит
  `apps/api/src/auth/auth.service.ts:87-91`: персональная ссылка многоразовая. `relink` пишет журнал и выдаёт новую ссылку,
  прежние не трогает (`apps/api/src/people/people.service.ts:183-204`); токены удаляются только при снятии доступа (`:239-248`).
- Проверки «прежняя ссылка после повторной выдачи не действует» в `verify-api` нет (`scripts/verify-api.mjs:455`,
  `:490` — только снятый и чужой).

**K7. Нет ограничения частоты входа** — подтверждено, тяжесть высокая.

- Пакета ограничения частоты нет (`apps/api/package.json:13-28`), ограничителя в `apps/api/src/main.ts:11-33` нет;
  в `apps/web/nginx.conf:8-13` нет `limit_req` и `limit_conn`; ответов 429 в `apps/api/src` нет.
- Ссылка по почте заводит строку `AuthToken` на каждый запрос без предела (`apps/api/src/auth/auth.service.ts:44-51`, `:72-85`).
- Пауза 60 секунд действует, только пока есть непогашенный код (`apps/api/src/auth/auth.service.ts:143-152`); шестая
  неверная попытка гасит код (`:188-200`), а поиск действующего кода видит только непогашенные (`:217-228`).
  Цикл «запрос кода, пять догадок, гашение» повторяется без паузы: вероятность угадать за цикл — 5·10⁻⁶,
  для 50 % — около 140 тыс. циклов, примерно миллион запросов (оценка чтением, прогоном не проверена).
- Маршрут кода открыт в любом режиме (`apps/api/src/auth/auth.controller.ts:41-46`); П-24 закрыл
  параллельный обход, «постоянного стража поверх HTTP нет» (`docs/13_FULL_AUDIT.md:68`).
- Просроченные токены не убираются (`apps/api/src/people/people.service.ts:248` — единственное удаление).

**Что предлагает бриф v2.0.** Вход по одноразовому коду, управление сессиями, персональные данные не
пишутся в журналы (бриф v2.0, §7.11).

## Рассмотренные варианты

| Вариант | Суть | Оценка |
|---|---|---|
| а | Оставить как есть | Три подтверждённых дефекта остаются |
| б | Сохранить многоразовую ссылку (решение № 1); токен — во фрагменте адреса и в теле запроса; новая ссылка гасит прежние; ограничение частоты своим кодом и настройкой nginx, без новой зависимости | Решённое не меняется; закрывает K5–K7 |
| в | То же, что «б», и срок ссылки короче — например, 30 дней | Меняет решение № 1 в части срока |
| г | Вход только по коду, как в брифе | Отменяет решение № 1; без отправщика SMS в промышленном режиме не работает |

## Предлагаемое решение

Вариант «б».

1. **Сразу, без кода приложения (K5).** В `apps/web/nginx.conf` — отдельный `location = /api/auth/consume`
   с `access_log off` (или журнал этого адреса в формате с `$uri` вместо `$request`). Тот же прокси,
   что у `location /api/`.
2. **Токен вне строки запроса (K5).** Ссылка выдаётся фрагментом адреса вида `${origin}/#вход/<токен>`:
   фрагмент на сервер не уходит. Веб-приложение уже разбирает адреса по `#` (П-50, `docs/13_FULL_AUDIT.md:94`;
   `apps/web/src/route.ts`): экран входа берёт токен, отправляет `POST /auth/consume` с токеном в теле
   (схема `consumeTokenSchema`, `packages/contracts/src/index.ts:67-69`), получает куку сессии и стирает
   фрагмент из истории браузера.
3. **Переходный срок (K5).** `GET /auth/consume?token=` сохраняется для ранее выданных ссылок с
   отключённым журналом (пункт 1) и снимается отдельным запросом после перевыпуска ссылок или по истечении
   их срока; дата снятия — решение заказчика при приёмке работы.
4. **Отзыв прежней ссылки (K6).** В `relink` в той же транзакции до выдачи — удаление прежних
   персональных ссылок человека (`deleteMany` по `userId` и назначению `FOREMAN_LINK`). Пометка `usedAt`
   не подходит: обмен персональной ссылки её не проверяет (`apps/api/src/auth/auth.service.ts:105`). Комментарии
   `apps/api/src/people/people.service.ts:16-17` и `:178-182` исправляются. Сессии, открытые прежней ссылкой, — по ответу
   заказчика: по умолчанию остаются до срока, как сегодня.
5. **Частота кодов (K7).** Пауза повторной выдачи отсчитывается от последнего выданного кода независимо
   от гашения; предел кодов на номер за час и за сутки — подсчётом строк `SMS_CODE` за окно по
   имеющемуся индексу `[userId, purpose]` (`apps/api/prisma/schema.prisma:623`). Отказ — 429 с текстом
   «Слишком много запросов. Повторите через N мин.». Ответ по-прежнему не различает существующий и
   несуществующий номер (`apps/api/src/auth/auth.service.ts:133-141`).
6. **Частота ссылок по почте (K7).** Предел живых ссылок на адрес — подсчётом строк `MAGIC_LINK` за окно;
   при превышении — прежний ответ «ссылка отправлена» без новой строки, чтобы форма не стала проверкой
   существования адреса (`apps/api/src/auth/auth.service.ts:47-49`).
7. **Граница и уборка (K7).** В nginx — `limit_req_zone $binary_remote_addr` для `location /api/auth/` с ответом
   429; за балансировщиком — `real_ip`. Просроченные токены убираются заданием по таймеру по образцу
   обезличивания заявок (`apps/api/src/leads/lead-retention.service.ts:32-36`). Предел по адресу
   запроса внутри API потребовал бы доверия к `X-Forwarded-For` (адаптер создаётся без настроек,
   `apps/api/src/main.ts:13`) и не вводится.
8. **Срок и многоразовость ссылки** — решение заказчика: «б» сохраняет 180 дней, «в» сокращает срок.
9. **Пакет `@fastify/rate-limit`** — не вводится: новая зависимость, только решением заказчика.
10. **Стражи `verify-api`**, каждый доказывается откатом: прежняя ссылка после повторной выдачи — 401;
    `POST /auth/consume` с токеном в теле открывает сессию; после гашения кода новый не выдаётся раньше
    паузы; предел кодов на номер срабатывает 429. Пределы задаются переменными окружения, чтобы стенд с
    десятками входов (`scripts/verify-api.mjs:38`, `scripts/seed-estimate.mjs:22`) не упирался в них;
    ступень nginx проверяется работой CI «Поставка» (`.github/workflows/ci.yml:287-329`).

## Последствия

- Решение № 1 не меняется: вход по ссылке без кода и регистрации остаётся.
- Ссылки, выданные до правки, работают до снятия `GET`; их перевыпуск — действие руководителя в «Людях».
- Скрипты, входящие по `GET /auth/consume`, переводятся на новый обмен вместе со снятием `GET`:
  `scripts/verify-api.mjs:38`, `:409`, `:433`, `:466`, `:605`, `:4606`; `scripts/seed-estimate.mjs:22`, `:286`;
  `scripts/capture-demo.mjs:24`; `scripts/verify-page.mjs:6089`, `:6346`.
- Ответ 429 — новый ответ API; экраны входа показывают его текст, как прочие отказы.
- Таблица токенов перестаёт расти без предела; при подключении отправщика (П-28) жертва не получит
  письма и SMS на каждый чужой запрос.
- Ни схема, ни зависимости не меняются. Доступ к журналу контейнера и балансировщика остаётся вопросом
  размещения (пункт 6.1 плана, `docs/06_PLAN.md:142`).
- Оценка: 3,5–4,5 идеальных дня (`ESTIMATE.md`, раздел 2).

## Зависимости от решений

- Вопрос раунда 1 о персональной ссылке входа и частоте запросов входа: выбор «а», «б», «в», «г».
- Вопрос раунда 1 об очереди работ после фазы 0: место этой работы относительно ADR-0007, ДР-11, ДР-12.
- Гашение сессий, открытых прежней ссылкой, и дата снятия `GET /auth/consume` — уточнения при ответе.
